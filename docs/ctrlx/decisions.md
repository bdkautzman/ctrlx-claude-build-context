# Decisions (and why)

Architectural choices of this kit and the reasons behind them. The rules that follow from them are in
`CLAUDE.md`; this file keeps the *why*, so a later session doesn't undo a deliberate choice.

* **Change an entry only with the user**, and record the reason and the date. Add new kit-wide decisions
  here (app-specific choices belong in the app's README).
* Found by experience (build errors, device behaviour)? That goes to `gotchas.md`; link it from here
  when it led to a decision.

Context: the kit was designed in a claude.ai conversation (Oct 2026) without a device, then verified
and extended in Claude Code on the ctrlX App Build Environment VM with a COREvirtual and a real CORE.
`reference/example-apps/` served as inspiration (ctrlx-cam-builder is the user's own repo).

| Decision | Reason |
|---|---|
| base `core24`, SDK 4.6.0, snapcraft 8.x | matches ctrlX OS 4.x; all SDK 4.6 samples use core24 |
| Web server = Python stdlib `http.server` on a Unix socket | no extra FOSS deps; socket-only is the App Guide recommendation |
| API under `/<snap>/api` listed as `restricted`; JWT scopes read without signature check | the reverse proxy validates tokens on restricted paths |
| Token passed via menu link `?token=${bearertoken}`, stored in sessionStorage | documented ctrlX pattern (SDK webserver sample) |
| Settings: `defaults/settings.json` (structure/types) + `src/app/settings_rules.py` (limits) | one generic validator + auto-generated settings form for every app |
| `copyOnLoad: true`, `writeProtected: false`, file watched by mtime | users can also edit settings.json in "Manage app data" |
| Data Layer writes are runtime-only, never persisted | PLCs may write cyclically → flash wear |
| Logging to stdout with `<N>` syslog prefixes | journald levels without bundling cysystemd |
| Menu target `_blank` (not `embedded`) | Bosch recommends `_blank` for 3rd-party UIs |
| Package-manifest schema v1.7 | released with ctrlX OS 4.4, superset of the v1.6 the samples use |
| `boschrexroth/ctrlx-actions` not used | last updated 2022, not suitable for core24 |
| No CI workflow (2026-10-21) | build locally for now (amd64 + arm64 in the build VM); the untested GitHub Actions template was removed |
| No ctrlX licensing (2026-10-21) | unofficial, unlicensed apps for now; licensing snippet and docs removed |
| No `menus.settings` entry (2026-10-21) | the ctrlX Settings page can't open `_blank` tiles; settings live in the app UI (gotchas #34) |
| Python package in `src/`, one `files` dump part, incremental builds (2026-10-22, template 0.1.4) | the build VM runs emulated (TCG): full builds take ~20 min, every snapcraft part costs 30-60 s per step; only Python changes should rebuild the venv (gotchas #47) |
| `.app` packages only on request (2026-10-22) | normal builds and tests use `.snap` files; one `.app` for both architectures costs both snaps' upload time (gotchas #48, #49) |
| UI tests in headless Chromium via Playwright, pinned, optional (2026-10-23) | Claude can look at screenshots and test on the device through the reverse proxy; QuickJS + DOM stubs (tried first) found script errors but no layout problems and needed stubs per app. Cost: one `sudo apt` line, ~1 min per run in the emulated VM, so not in every `check.sh` (gotchas #51, #52) |
| PDF reports with a stdlib PDF writer, checked with `tools/pdf_check.py` (2026-10-25, ctrlx-network-scanner) | the user asked for open-source libraries only; reportlab and fpdf2 both need Pillow (C extension: aarch64/cp312 wheels, ~10 MB, more RAM) for text-only reports. A ~250-line writer with the PDF standard fonts (widths from Liberation Sans) covers tables and pages. pypdfium2 (Apache/BSD) renders the result to PNG in the UI test venv only - never in a snap |
| Generic fixes found while building an app go back into the template/tools/docs (since 2026-10-21) | the kit gets better with every app; each app's CHANGELOG / `apps/README.md` notes what was brought back. New tools still need the user's OK first (next row) |
| Custom tools only after asking the user (2026-10-25, user's request) | `ctrlx-network-scanner` cost about twice the tokens of earlier first builds (10.4M effective vs ~5M), partly from tools built for that one case without asking: a PDF writer with font metrics, a PDF render check, an rtnetlink parser, a device scan script, a new `ctrlx.py` command and an extra dev dependency. Each one costs writing, testing and context that every later step re-reads. Asking first (library / small custom version / smaller feature, with rough size) lets the user weigh that cost. Rule in CLAUDE.md, checklist in skill `new-ctrlx-app`, the reviewer agent flags tools without a note that the user agreed |
| RAM guideline 75 MB per app stays; an app likely to exceed it asks the user first (2026-11-03, user's request) | App Guide 6.2. `ctrlx-barcode-reader` needs more (OpenCV + numpy + 5 MP camera frames): the user accepted that for this app only and asked that other apps do the same - estimate early, ask, record the exception (rule in CLAUDE.md, checklist in skill `new-ctrlx-app`). New figure for this app ~100 MB since 0.2.0 (user, 2026-11-04): idle is already ~76 MB, so 75 MB would mean replacing a library |
| Binary Python wheels (C extensions) and Ubuntu packages with native code get their own snap parts (`wheels`, `debs`), installed for the build-for architecture (sha256 pins / exact package list) (2026-11-03, ctrlx-barcode-reader, gotchas #99) | the python plugin's pip runs on the amd64 build VM and would put x86_64 wheels into an arm64 snap; `pip install --platform ... --target` in part `wheels` (`apps/ctrlx-barcode-reader/snap/snapcraft.yaml`, `wheels/requirements.txt`) gets the right ones, and a change in `src/` doesn't download them again |
| Every app keeps a `KNOWN-ISSUES.md` working document (2026-11-03, user's request) | findings of an app (e.g. ctrlx-barcode-reader: a camera that ignores software triggers, packet loss on the CORE) were spread over CHANGELOG, README, gotchas and the conversation; one document per app with evidence, attempts, status, untested parts and the diagnostic commands keeps them available for later analysis. Template file + CLAUDE.md "Definition of done" 6, skills `new-ctrlx-app` / `record-gotcha`, reviewer agent |
| amd64 tests run on a real amd64 CORE (X5, X7) when one is available, not on the COREvirtual (2026-11-04, user's request) | performance figures from real hardware hold in real use; the COREvirtual is a VM with a different CPU (gotchas #98). The COREvirtual stays for when there is no real amd64 CORE, and for checks that need SSH when the real CORE has no SSH login or doesn't allow SSH (scripts in the app's sandbox, kernel logs, `/proc`); the rest of such a test still runs on the real CORE, over REST and the UI |
| CORE hardware manuals: facts in our own words + links are committed, the PDFs stay local and git-ignored (2026-11-04, user's request to add them to `reference/`) | the facts decide RAM, flash, port and USB limits for apps; the manuals are all rights reserved, including reproduction and distribution, and the repository has a GitHub remote |
| Installing an app and `--service` on the devices in `devices.toml` need no asking during active app development (2026-11-04, user's request) | whoever uses the kit expects the devices to be used for testing, also when other apps run on them. Other snaps and device settings such as `--allow-unknown` stay off limits unless the human asks |
| The template is a starting point; apps may drift from it. What several apps need (or a very basic function) goes into the template once (2026-11-07, user's feedback on a review of the five apps) | copies that differ are fine - each app grows its own way. To avoid: later apps building the same feature again, each in its own way (settings drawer, help/tutorial, widget, downloads, uploads, JSON nodes were built 2-5 times). Template 0.2.0 took those in; older apps are not changed |
| Three roles view / operate / configure (scopes `.web.all.r`, `.web.operate.x`, `.web.all.rw`) in the template (2026-11-07, user's request) | two levels (read / read-write) forced a choice between "operators may change the settings" and "operators may not trigger anything"; amr-fleet and core-connector hid settings from read-only users on their own. ctrlX OS's services use the same three levels. The old scope ids stay (view, configure), so apps made before keep their users' permissions. Settings are configure-only, reading included |
| Shared UI parts in `www/kit.js` / `kit.css`, apps keep their code in `app.js` (template 0.2.0, 2026-11-07) | every app had copied token handling, `api()`, the settings form and the ready marker into its `app.js`; two apps built the drawer and the tutorial. A separate file shows what is the kit's and can be replaced by a newer one |
| Home screen widget in the template with `noInitialCreation: true` (2026-11-07) | two apps added a widget; ctrlX OS puts a new app's widget on every user's home screen unless the flag is set - a new app should not do that before it is decided |
| Snap names: company part optional, defaults in a git-ignored `kit.toml` (2026-11-07, user's request) | all five apps are `ctrlx-<app>` while the rule said `ctrlx-<company>-<app>`; the App Guide asks it of ctrlX World Partners (only relevant for a validation, where a rename means a settings migration). `kit.toml` (company, author, url) saves the questions per new app; git-ignored like `devices.toml`, because the kit may be shared |
| PLC commands use Execute / Busy / Done / Error (`PlcCommand`, template 0.3.0; 2026-11-07, user's choice between that, a request id, or both) | four apps had four schemes (start string + abort bool, trigger reset by the app, request id, marker string); one known pattern lets a PLC programmer use every kit app the same way. PLCopen style was chosen over a request id (one write per command) because PLC programmers know it from function blocks |
| Missing Data Layer at start or after a state switch: INFO, ERROR only after 60 s (template 0.3.0, 2026-11-07) | every kit app wrote "provider start failed: CLIENT_NOT_CONNECTED" as an error into the Logbook at every boot, although it is expected and fixed seconds later (gotchas #28) |
| CPU/RAM of an app on a device: the System Analyzer is the instrument, no measuring script per app (2026-11-07, user's request) | every app measured with its own commands or script (amr-fleet `perf_test.py`, MainPID + `/proc` recipes); the analyzer already samples every app every 5 s and answers over REST (`apps/summary`, CSV export) - `build-deploy-test.md` §5 |
| `gotchas.md` is read through a topic index at its top, not as a whole (2026-11-08, user's choice of option A) | at 110 entries the file is ~17k tokens, and whatever a session reads stays in its context for every later turn; the skills said to read it "when anything fails". Grep for the error text or read the index (~1.3k tokens), then only the entries it names. Not chosen yet: splitting it into topic files, distilling settled lessons into the topic docs, archiving closed KNOWN-ISSUES entries of the apps |
| Data Layer nodes accept only their own type; the template has every scalar type and `array-of-<type>` (template 0.4.0, 2026-11-08, user's choice) | a PLC writes with its variable's type (REAL = float32), and the template had only float64/int64/uint64 nodes: the X3 answered `DL_TYPE_MISMATCH` for every other type (gotchas #111). Accepting other types (widening REAL into float64) was ruled out: no place where a value can change on the way. So a node gets the PLC variable's type instead |
| The template has a Data Layer client, `DataLayerClient` (template 0.4.0, 2026-11-08, user's request) | core-connector's `ClientAdapter` was the only client of the kit, verified on three devices (read, JSON, metadata, bulk, result names, empty values); without it in the template the next app that reads a PLC variable would write a second one. Moved without the app-specific calls; opt-in (`on_client`), so apps that only provide nodes open no client. Subscriptions are not in it yet |
| UI feedback from the page: a dev-only overlay (Alt+click an element, type a note) + skill `/ui-feedback` (2026-11-09, user's request, idea from a chat about faster UI prototyping) | describing a UI change in words ("the second button in the top right") is slow and vague; a note fixed to an element (selector, structure path, text, size, window size) tells Claude exactly what is meant. The script lives once in `tools/ui-feedback/`, not in `www/`, so it never goes into a snap or differs between apps; the app's dev server adds it only when `run-local.sh` sets `APP_DEV_FEEDBACK` and auth is off (`APP_DEV_NO_AUTH=1`), so neither the snap nor `ui_check.py` shows it. Notes in `.dev/feedback.json` (git-ignored, read on every request so the skill can mark them while the server runs). The Python side (`dev_feedback.py`, ~100 lines) is inert in the snap. Not chosen: a browser extension (one more thing to install on the PC) |
| The user checks a new or changed UI on the `run-local.sh` page, with feedback loops (`/ui-feedback`), before the snap is built (2026-11-09, user's request) | UI wishes found after a build cost a snap round trip each (build, a full one ~20 min in the VM; install in SERVICE state; open through the reverse proxy), while on the dev page a fix shows after a reload. Claude's own `ui_check.py` look comes first, so the user doesn't review a broken page. A build needed earlier for something that isn't the UI (Data Layer, interfaces on a device): ask. Local page = admin only; the other roles' views come from `ui_check.py --role`, the ctrlX integration (sidebar, proxy, home screen widget) from the device after the build |
