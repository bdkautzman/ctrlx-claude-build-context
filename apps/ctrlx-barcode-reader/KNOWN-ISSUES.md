# Known issues and caveats - ctrlx-barcode-reader

Working document: everything that does not work as expected, works only with a workaround, or was not tested,
with the evidence, what was tried and what is still open. Keep it current: add new findings, mark fixed ones
(don't delete them - the history helps the next analysis), and date every entry. Generic lessons also go to
`docs/ctrlx/gotchas.md` (numbers in brackets).

Test setup of all findings below (2026-11-03): camera **Omron Sentech STC-MCS500POE**, firmware 20.50, serial
21DC415, 192.168.1.99/24, BayerRG8 2448 x 2048, PoE; **real ctrlX CORE** 192.168.1.7 (arm64, ctrlX OS 4.6, XF10 in the
camera's network, MTU 1500); **ctrlX COREvirtual** in ctrlX WORKS with port forwarding (amd64, QEMU NAT 10.0.2.15);
app 0.1.0 with Aravis 0.8.30 (Ubuntu 24.04), PyGObject 3.48.2, OpenCV 4.14.0.94, numpy 2.3.5, zxing-cpp 3.1.1.

## 1. Software trigger of the STC-MCS500POE produces no frame (open)

**Symptom** (real CORE, 2026-11-03): with the camera in software-trigger mode every read ended with
`no image within 3000 ms`; the stream statistics showed not a single packet (0 completed, 0 missing), the CORE's
interface counters showed no stream traffic at all - the camera never started an exposure.

**Camera state at that time** (read through Aravis and GVCP READREG): control privilege CCP = 2 (the app),
stream destination SCDA0 = 192.168.1.7, SCP0 = the app's stream port, SCPS0 = 1444/1520 B with DoNotFragment,
SCSP0 = 49152; TriggerSelector = FrameStart, TriggerMode = On, TriggerSource = Software, TriggerActivation =
RisingEdge, AcquisitionMode = Continuous, `AcquisitionEnabledReg` = 1 (running), `AcquisitionLocked` = 1,
`AcquisitionBurstFrameCount` = 1, `AcquisitionFrameCount` = 1, ExposureMode = Timed, `SoftwareAvairable` = 1.

**What the camera's GenICam XML says** (dumped with `arv-tool-0.8 -a 192.168.1.99 genicam`):
* `TriggerSoftware` (Command, CommandValue 1) is locked by `TriggerSoftwareEnabled` =
  `TRIGGERMODE = 0 ? 1 : (TRIGGERSOURCE = 1 ? 0 : 1)`; TriggerSource "Software" has the raw value 1, so with
  TriggerMode On it is unlocked (read back: `TriggerSoftwareEnabled` = 0).
* Its value goes through `TriggerSoftwareValue` (IntConverter): `SHIFT = SEL=0 ? 0 : (SEL=1 ? 4 : (SEL=2 ? 1 :
  (SEL=3 ? 3 : 2)))`, written value `1 << SHIFT`, SEL = TriggerSelector (FrameStart = 0) → writes 1 to
  `TriggerSoftwareReg` = `AcquisitionControlAddressBase` + 0x28 (IntReg, 4 bytes, big endian, WO).
* `FrameTriggerModeReg` = base + 0x2C (bits 31:30), `FrameTriggerSourceReg` = base + 0x30 (bits 31:28),
  `TriggerSource` is locked while TriggerMode is On (`TriggerModeEnabled`) - Aravis' `set_trigger()` writes the
  mode before the source (here the source was already Software, so this did not matter).
* TriggerSource values: Software 1, Line0 2, Line1 3, Line2 4, Line3 5, SoftwareSignal0-3 7-10, Action0 11,
  LogicBlock0 12. TriggerSelector: FrameStart 0, ExposureStart 1 (+ AcquisitionStart in `dup_available_triggers`).

**What was tried** (all inside the app's snap on the CORE, see "Diagnostics"):

| Attempt | Result |
|---|---|
| `cam.set_trigger("Software")`, `start_acquisition()`, `cam.software_trigger()` | no frame |
| `clear_triggers()`, TriggerSelector FrameStart, TriggerSource Software (mode Off), then TriggerMode On, start, `dev.execute_command("TriggerSoftware")` | no frame |
| direct write `TriggerSoftwareReg` = 1 | no frame |
| TriggerSource SoftwareSignal0, `SoftwareSignalSelector` SoftwareSignal0, `SoftwareSignalPulse` | no frame |
| `AcquisitionBurstFrameCount` set to 1 explicitly | no frame |
| free run (TriggerMode Off, Continuous, 5 fps) | **frames arrive** |
| AcquisitionMode SingleFrame, AcquisitionStart per frame | **frames arrive** (14 of 14 complete with 40 µs pacing) |

No exception, no GVCP error status for any of the writes (Aravis would raise one).

**Workaround in the app**: `camera.acquisition` = `singleframe` - AcquisitionStart → one frame →
AcquisitionStop per read (plain GenICam, a fresh exposure per read, ~208 ms for 5 MP at 20 ms exposure).
Cost compared to a working software trigger: two extra GVCP commands per read (a few ms) - negligible.

**Open questions / next steps for the analysis**:
1. Does the software trigger work with Sentech's own software (StViewer / StApi on a PC) with the same firmware?
   If not: firmware issue (ask Omron Sentech, check for a firmware update).
2. Capture the GVCP traffic of `TriggerSoftware` (tcpdump/Wireshark on a PC in the camera's network, or a port
   mirror): which register and value is really written, and the ACK status.
3. Read `AcquisitionStatus` / `FrameTriggerWait` through `AcquisitionStatusSelector` (the XML has a
   `FrameTriggerWait` enum entry, not readable as a plain feature) before and after the trigger.
4. Enable the camera events `FrameTrigger` / `FrameTriggerMissed` (EventSelector, EventNotification) and watch
   them (Aravis `ArvGvDevice` "event"): does the camera register the trigger at all?
5. Try a newer Aravis (0.8.3x / 0.9) - the Ubuntu 24.04 package is 0.8.30.
6. Try TriggerSelector ExposureStart, TriggerActivation AnyEdge, a non-zero TriggerDelay.
7. Hardware trigger on Line0 (a sensor or PLC output) was not tried.

## 2. Image packets lost on the ctrlX CORE (worked around)

ctrlX OS sets `net.core.rmem_max` = 212992 (both devices; an app can't raise it): the stream socket holds ~145
packets, ~2.5 ms of a camera sending at 1 Gbit/s. The camera's default inter-packet delay (GevSCPD 6000 ticks ≈ 6 µs)
lost whole frames on the CORE; Aravis' resend requests could not always catch up.

Measured with SingleFrame acquisition, 5 MP BayerRG8, 6 frames each (frame time incl. 20 ms exposure):

| Packet delay | Complete frames | Resent / missing packets | Time per frame |
|---|---|---|---|
| 6 µs (camera default) | 4 of 6 | 1271 / 5370 | 99-189 ms |
| 20 µs | 3 of 6 | 7430 / 7218 | 214-396 ms |
| **40 µs** | **6 of 6** (later 8 of 8, 80 reads in a row 0 failed) | 45 / 0 | 208 ms |

(20 µs was worse than 6 µs - the loss is not linear; not analyzed further.) Interface counters of XF10 never showed
drops/length errors; the loss is in the socket buffer. Default now `camera.packetDelayUs` = 40 (Aravis converts it
to camera ticks with `GevTimestampTickFrequency`). With 0.5 s exposure the reads took ~1.1 s each; continuous reading
at 1/s used 57 % of one CORE core.

Open: try smaller payloads (camera ROI, binning - `BinningHorizontal/Vertical` exist) for faster frames with less
pacing; Aravis stream properties `frame-retention`, `packet-timeout`, `packet-request-ratio` were left at their
defaults; jumbo frames are not possible (MTU 1500 on the CORE).

## 3. COREvirtual with port forwarding gets no images (by design)

The COREvirtual (and the build VM) sit behind QEMU user networking: their only address is 10.0.2.15, all traffic
leaves through the Windows PC. GVCP is request/answer, so the answers come back through the NAT: opening the camera,
reading/writing features, discovery by IP address work. The image stream is sent by the camera on its own to the
address the app writes into `GevSCDA` (10.0.2.15) - unreachable from the LAN, so every read ends after
`camera.timeoutMs` with "this device has the NAT address 10.0.2.15 ...". Broadcast discovery never leaves the
virtual network. Workarounds: `camera.source` = `simulated` (Aravis' fake camera + generated codes), or a COREvirtual
with a network adapter in the camera's network (not tested). Details: gotchas #93.

## 4. numpy >= 2.4 on the COREvirtual (fixed)

The COREvirtual reports the host CPU (i7-11850H) **without** SSSE3, SSE4.1, SSE4.2, POPCNT (but with AVX, AVX2,
AVX-512F). numpy 2.4+ x86_64 wheels need x86-64-v2 and raise `RuntimeError` at import. `flatbuffers` (used by
`ctrlxdatalayer`) imports numpy when it is installed and catches only `ImportError` → the Data Layer did not start
either. Fix: numpy 2.3.5 (baseline SSE3) + `main._check_numpy()` blocks an unusable numpy so the Data Layer still
works and every read reports the error. OpenCV 4.14 (baseline SSE3) and zxing-cpp run on that CPU. Gotchas #98.
Caveat for updates: check a new numpy/OpenCV/zxing-cpp wheel's x86 baseline before raising a pin.

## 5. arm64 snap with amd64 Ubuntu libraries (fixed)

Snapcraft 8 in the build VM (amd64, destructive mode) staged the BUILD machine's packages for `stage-packages`
in an arm64 build; with `:${CRAFT_ARCH_BUILD_FOR}` it fetched arm64 packages but no longer filtered those core24
already has (python3.12, libffi, ...). The python plugin's pip would equally install x86_64 wheels. Fix: part `debs`
(`apt-get download <pkg>:$CRAFT_ARCH_BUILD_FOR` of exactly 9 packages, versions in
`usr/share/ctrlx-barcode-reader/debs.txt`) and part `wheels` (`pip install --platform ... --require-hashes`).
Check after every arm64 build: `find prime -name '*.so*' -type f -exec file {} + | grep ELF | grep -v aarch64` → nothing.
Also: an incremental build that reprimes after a `prime:` filter change keeps the old files - build `--clean`.
Gotchas #99.

## 6. Discover returned an empty list once (open, intermittent)

2026-11-03 on the CORE: the first `POST /cameras/discover` answered `[]` while the camera was open in the app; the
same discovery in a separate process in the app's sandbox found it at once (Aravis log: "Device
'OMRON SENTECH-STC-MCS500POE-21DC415' found (interface 192.168.1.7)"), a manual broadcast to 255.255.255.255 and to
192.168.1.255 was answered, and the next two calls of the app found the camera. Not reproduced, cause unknown
(timing of the 1 s Aravis discovery window? a camera busy with the stream?). Workaround: press Discover again, or
enter the IP address (the app opens the camera by address, discovery is only a helper).

## 7. One controlling application per camera

GigE Vision allows one application with control privilege (+ heartbeat). Two devices with this app and the same
`camera.address` fight over the camera: only one opens it. Seen during the tests: the COREvirtual held the camera
(through the NAT) until it was switched to the simulated camera. The app keeps control while it runs (also
without reads) and gives it free when it stops or `camera.source` / `camera.address` change. GVCP READREG works
from a second application without control (used for the diagnostics).

## 8. Memory

Real CORE: RSS 128 MB (RssAnon 82 MB, RssFile 46 MB), steady over idle, continuous reading and 50 history entries;
systemd reported a memory peak of 143.5 MB for the service. COREvirtual: 97 MB. `import numpy, cv2, zxingcpp` alone
~46 MB. Above the App Guide's 75 MB - accepted by the user for this app. Candidates to reduce it: fewer stream buffers
(`camera.buffers` 2 → each 5 MB), a smaller `images.historySize` / `images.displayWidth`, not keeping the last full
frame (needed for the PNG download).

## 9-10. Fixed web/startup problems

* **502 from the reverse proxy**: the history table loaded 50 thumbnails at once; Python's `socketserver` listen
  backlog is 5. Fixed: backlog 64 (also in template 0.1.8), the page loads 3 thumbnails at a time. Gotchas #102.
* **First start after the install**: the app data folder existed but was not writable for ~2 s (gotchas #82); the
  app crashed once and systemd restarted it. Fixed: `main._load_settings()` retries (template 0.1.8).

## 11. Possible wrong EAN-13 reads

In the simulator a noisy EAN-13 tilted by 6° gave zxing-cpp a second, **wrong** EAN-13 with a valid check digit
(EAN-13 has only a mod-10 check digit). The simulator now tilts 1D/stacked codes at most ±3°. Real labels: restrict
`decode.formats` to the symbologies in use; a PLC should check the plausibility of `result/codes`.

## 12-17. Smaller caveats

* **Packet size 1520 B**: Aravis' negotiation (`camera.packetSize` = 0) chose 1520 B with DoNotFragment on the CORE
  (interface MTU 1500) and those frames arrived complete. If frames ever break after a network change, set 1444.
* **Stream port**: Aravis 0.8.30 binds the stream socket to a port the OS chooses (32768-60999, which includes the
  ports reserved on ctrlX OS 49250-50250); the app opens the stream again if it gets a reserved port. No fixed port.
* **OpenSSL 1.1.1k** (end of life) is bundled in the OpenCV wheel for FFmpeg's network protocols; the app never
  opens videos or streams with OpenCV. Watch for an OpenCV wheel with a newer OpenSSL.
* **GLib typelibs**: Ubuntu's `gir1.2-glib-2.0` 2.80.0-6ubuntu3.10 runs on core24 20260824's GLib
  2.80.0-6ubuntu3.8 (same upstream release). A core24 update with another GLib could need a new build.
* **Fake camera** (simulated mode): it keeps producing frames between reads (stream "underruns" count up, 1124 after
  a few minutes); results are right (stale frames are discarded before each read), cost 0.2 % CPU idle.
* **AppArmor**: one denial `open /proc/<pid>/mounts` by python3 at start - every kit app shows it; harmless.

## 18. FOSS

`configs/package-assets/ctrlx-barcode-reader.fossinfo.json` (22 components, ~600 KB of license texts) was generated
on 2026-11-03 by a throwaway script from: the wheels' license files (`*.dist-info/LICENSE*`, OpenCV's
`LICENSE-3RD-PARTY.txt`, numpy's `LICENSE.txt` incl. GCC runtime exception), license files fetched for parts the
wheels don't list (libtiff 4.7.1 `LICENSE.md` from OpenCV 4.14.0 `3rdparty/libtiff`, KleidiCV 26.03
`LICENSES/Apache-2.0.txt`, carotene's BSD header from OpenCV `hal/carotene`, nanobind `LICENSE`) and the Debian
`copyright` files in `prime/usr/share/doc/*/`. That script is not in the kit. **When a pinned version changes, the
fossinfo and `ctrlx-barcode-reader.foss-offer.txt` must be redone** - a kit tool for it would be a new tool (ask the
user first; candidate: extend `tools/foss_from_prime.py` with wheel license files and Debian copyright files).

## 19. Not tested yet

* Real camera: only one symbology (Code 128 label X004WHVORB, 5 of 5 decoded, ~1.15 s per read at 0.5 s exposure);
  all others only with simulated images.
* Image storage on a removable medium on a device (unit tests only; the CORE has a USB stick `/media/sda1`).
* Decode region, PNG download, settings drawer on a device (locally in headless Chromium only); live picture on the
  CORE only through the API.
* Auto exposure / auto gain with SingleFrame acquisition (each read is one frame - the camera's auto loop may not
  converge); the test used fixed 0.5 s / gain 100 in a dim room.
* Long runs (hours/days, memory growth), many reads per second, a PLC writing `trigger` / `request-id` (tested
  through REST only), save/load of the settings with ctrlX configurations.
* Other GigE Vision cameras; pixel formats other than BayerRG8 on the real camera (Mono8 exists).

## Diagnostics (how the findings were made)

**Run Python in the app's own sandbox** (same Python, libraries, confinement - as root). The app must release the
camera first: set `camera.source` = `simulated` in the settings. Then, from the build VM:

```bash
B64=$(base64 -w0 test.py)
python3 tools/ctrlx.py --device core ssh "echo $B64 | base64 -d | sudo ARV_DEBUG=stream:2 snap run --shell ctrlx-barcode-reader.service -c 'python3 -'"
```

`ARV_DEBUG` categories used: `stream:2` (stream statistics, packet timing histogram), `interface:3` (discovery).
A test script starts with:

```python
import sys, time
sys.path.insert(0, "/snap/ctrlx-barcode-reader/current/lib/python3.12/site-packages")
from app.camera import load_aravis          # puts gi + the Aravis typelib on the paths
ar = load_aravis()
cam = ar.Camera.new("192.168.1.99"); dev = cam.get_device()
cam.gv_set_packet_size(1444); cam.gv_set_packet_delay(40000)           # ns
dev.set_stream_options(ar.GvStreamOption.PACKET_SOCKET_DISABLED)
stream = cam.create_stream(None, None)
for _ in range(2):
    stream.push_buffer(ar.Buffer.new_allocate(cam.get_payload()))
cam.clear_triggers(); cam.set_acquisition_mode(ar.AcquisitionMode.SINGLE_FRAME)
cam.start_acquisition(); buf = stream.timeout_pop_buffer(3_000_000); cam.stop_acquisition()
print(None if buf is None else buf.get_status().value_nick,
      ar.Stream.get_statistics(stream), ar.GvStream.get_statistics(stream))   # completed/failures/underruns, resent/missing
# software trigger instead: cam.set_acquisition_mode(CONTINUOUS); cam.set_trigger("Software");
#   cam.start_acquisition(); cam.software_trigger(); ...  dev.get_feature("TriggerSoftwareEnabled").get_value_as_string()
```

**Camera registers without control** (GVCP READREG from any machine in the network, stdlib only):

```python
import socket, struct
regs = [0x0A00, 0x0A04, 0x0A14, 0x0D00, 0x0D04, 0x0D08, 0x0D18, 0x0D1C]   # CCP, primary app port/IP, SCP0, SCPS0, SCPD0, SCDA0, SCSP0
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); s.settimeout(2)
body = b"".join(struct.pack(">I", a) for a in regs)
s.sendto(struct.pack(">BBHHH", 0x42, 0x01, 0x0080, len(body), 7) + body, ("192.168.1.99", 3956))
data = s.recv(1024); print([hex(v) for v in struct.unpack(">%dI" % len(regs), data[8:8 + 4 * len(regs)])])
```

(GVCP discovery: send `struct.pack(">BBHHH", 0x42, 0x11, 0x0002, 0, 1)` to UDP 3956; the answer holds MAC, IP,
manufacturer, model, firmware, serial, user name at fixed offsets.)

**Network counters on the CORE** (before/after a read): `ip -s -s link show XF10`, `grep ^Udp: /proc/net/snmp`
(RcvbufErrors), `/proc/net/udp` (drops of the stream socket), `ss -uanp` (the app's sockets). Firewall:
`sudo iptables -S`, `sudo iptables-legacy -S` (both empty, policy ACCEPT on 2026-11-03).
**Sandbox denials**: `sudo journalctl -k -b | grep 'apparmor="DENIED"' | grep barcode` and `grep type=1326` (seccomp).
**CPU/RAM of the app**: `pid=$(systemctl show -p MainPID --value snap.ctrlx-barcode-reader.service.service)`, then
`/proc/$pid/stat` fields 14+15 over time and `VmRSS`/`RssAnon` in `/proc/$pid/status`.
**Camera features / GenICam XML from the build VM** (no root): `apt-get download libaravis-0.8-0 aravis-tools-cli`,
`dpkg-deb -x` into a folder, `LD_LIBRARY_PATH=<folder>/usr/lib/x86_64-linux-gnu <folder>/usr/bin/arv-tool-0.8 -a
192.168.1.99 values` (or `genicam`, `control <Feature>`).
